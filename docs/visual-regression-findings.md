# Visual Regression Tooling: Findings

Spike: [STA-143](https://linear.app/state-machine/issue/STA-143). Companion to
[TESTING.md](../TESTING.md) section 3, "Planned third layer".

## Recommendation

**Adopt the self-hosted option.** Use the `toMatchScreenshot` assertion that
Vitest browser mode already provides, inside the play functions of the existing
`storybook` Vitest project.

It costs nothing, it adds no new runner, and it works in this repository today.
The three hosted services all price by the snapshot, and our snapshot count per
run is about 1000. That puts every hosted free tier out of reach after four CI
runs a month.

Two limits come with this choice, and both are in the implementation ticket:

1. Baselines must be generated by CI, never by a developer machine. Font
   rendering differs between operating systems.
2. The first rollout covers layout-bearing components and pages, not all 252
   stories. Volume is the main source of review noise.

## What This Layer Must Catch

Play tests assert behaviour. They pass while the spacing jumps, the gradient
stops flowing, or the serif heading falls back to a sans font. Only a pixel
comparison catches those three.

The immediate trigger is STA-179. The app now ships a light theme and a dark
theme, so the visual surface doubled. Sign-off for STA-179 was a person looking
at hand-captured screenshots across two themes and two widths. That does not
scale.

Three further facts came out of a working experiment in this repository, not

- `expect.element(...).toMatchScreenshot()` runs inside a Storybook play
  function under the existing `storybook` project. No new project, no new
  runner, and no new dependency.
- A story sets its own theme with `globals: { theme: "light" }`. Both themes

  [.storybook/preview.ts](../.storybook/preview.ts).
- A story sets its own width with `page.viewport(width, height)` from
  `@vitest/browser/context`.

The theme matrix and the viewport matrix need no vendor feature. They are two
loops in a helper.

## The Snapshot Budget

Every hosted service bills per snapshot, and a snapshot is one story in one
theme at one width. The Tailwind responsive prefixes in `src` are `sm` (23
uses), `md` (17), `lg` (13), and `xl` (2), so two widths is the floor and three
is realistic.

| Matrix | Snapshots per CI run |
| --- | --- |
| 252 stories, 2 themes, 2 widths | 1008 |
| 252 stories, 2 themes, 3 widths | 1512 |

A PR gate runs on every push. Ten pushes a month is a quiet month for this
repository. That is 10,000 snapshots against a 5,000 free allowance.

## The Candidates

### Chromatic

The `@chromatic-com/storybook` addon already ships in
[.storybook/main.ts](../.storybook/main.ts), so the wiring cost is the lowest of
the four. One `chromatic --project-token` step in CI, and the service builds
Storybook and captures every story.

Strong points:

- The baseline review workflow is the best of the four. Snapshots are approved
  in a web UI, the approval is tied to the commit, and a GitHub check goes green
  when the author accepts the change.
- Modes handle the theme matrix and the viewport matrix as first-class
  configuration.
- Anti-aliasing noise is handled by the service, and the diff threshold is
  configurable per story.
- Storybook maintains it, so the version moves with Storybook.

Weak points:

- Cost. The free allowance is 5,000 snapshots a month. Our matrix spends that in
  four CI runs. The Starter plan is listed at 179 USD a month for 35,000
  snapshots, which is about 34 runs. Overage is listed at 0.008 USD a snapshot,
  which is about 8 USD a run past the allowance.
- A mode multiplies the count. Two themes at two widths is four snapshots per
  story, so the bill grows with the exact matrix this layer exists to cover.
- The build runs on the vendor's infrastructure, so CI depends on a third party
  being reachable.

### Percy

Percy is the BrowserStack product in this space. It captures the DOM and
re-renders it in the vendor's browsers.

Strong points:

- The review UI is mature and close to Chromatic's.
- The free allowance is also 5,000 screenshots a month, with unlimited users and
  projects.
- The Storybook integration takes a built static Storybook, so it does not care
  about our Vitest wiring.

Weak points:

- Cost is unclear. BrowserStack removed the public Percy pricing page, and paid
  tiers now go through sales. Third-party sources put the cheapest tier at 599
  USD a month. This spike did not verify that figure.
- The same snapshot arithmetic applies, so the free tier lasts four runs.
- DOM capture and vendor-side re-rendering means the picture under review is not
  the picture our Chromium produced. Font loading differences show up here.
- Buying it adds a vendor relationship that nothing else in this stack needs.

### Lost Pixel

Lost Pixel is an MIT-licensed runner with an optional hosted platform. The
runner reads a built Storybook, captures each story with Playwright, and diffs
against baselines committed in the repository.

Strong points:

- The runner is free, and the baselines stay in our repository.
- The GitHub Action gives a review flow without the hosted platform. A label or
  a bot command accepts the new baselines.
- Storybook support is a first-class mode, not a generic page crawl.

Weak points:

- It is a second runner. It needs `npm run build-storybook`, its own Playwright
  browser download, and its own config file, next to the browser runner we
  already pay for in CI time.
- The theme matrix needs its own wiring, because Lost Pixel drives the Storybook
  iframe by URL. Theme and viewport become URL parameters we construct, which
  duplicates what `globals` and `page.viewport` already do in the Vitest run.
- The hosted platform is priced between 100 and 670 USD a month, so the free
  path is the self-hosted path with extra steps.
- Project activity is thinner than the other three. A single-maintainer
  dependency in the CI gate is a risk worth naming.

### Self-Hosted Vitest Screenshots

Vitest 4 browser mode ships `toMatchScreenshot`. This repository runs Vitest
4.1.11 with the Playwright provider, so the assertion is available now.

How it behaves, verified here:

- The baseline path is
  `<story dir>/__screenshots__/<story file>/<name>-<browser>-<platform>.png`.
  Browser and platform are in the file name, so a Linux CI baseline and a macOS
  baseline never collide.
- The first run writes the baseline and **fails** the test. A new baseline never
  passes silently, which is the property a CI gate needs.
- The comparator is `pixelmatch`. Anti-aliased pixels are detected and ignored
  by default (`includeAA: false`), the colour threshold defaults to 0.1 in YIQ
  space, and `allowedMismatchedPixels` or `allowedMismatchedPixelRatio` set the
  failure budget.
- Three consecutive runs against the same baseline passed with zero mismatched
  pixels.

Strong points:

- Zero cost and zero new dependencies.
- No second runner. The screenshots ride the `storybook` project that CI already
  runs in 25 seconds.
- The full matrix is ours. Themes come from `globals`, widths come from
  `page.viewport`, and neither is metered.
- Baselines are version controlled, which AGENTS.md requires of documentation
  and which makes a visual change part of the diff a reviewer already reads.
- Anti-aliasing handling is the same `pixelmatch` algorithm the open-source
  tools use.

Weak points:

- No review UI. The approval workflow is a Git diff of PNG files in the GitHub
  "Files changed" view, plus a job that regenerates baselines on demand.
- Baselines are binary files in the repository. At roughly 1 to 30 KB each, a
  1000-snapshot matrix adds a few megabytes, and every intentional redesign
  rewrites them.
- Baselines are platform-specific. A developer who regenerates them on macOS
  breaks the Linux CI job, so the update path must run in CI.
- The failure output is a PNG in a CI artifact, not a hosted link. Reading a
  failure takes one more step than a hosted service.

## Sketch: CI Wiring

The gate stays consistent with the STA-141 gates. It is one more step in
`.github/workflows/ci.yaml`, in the same job, after the existing UI step.

1. Add a helper in `.storybook/` that takes a story name and runs the matrix.
   The helper loops the widths with `page.viewport`, and each theme is a
   separate story export with its own `globals`.
2. Call the helper at the end of the play function of each story that carries
   layout. The assertion is the last step of the play function, so the shape in
   TESTING.md section 1.2 holds. One play function still ends in one assertion.
3. Commit the baselines that CI generates under `src/**/__screenshots__/`.
4. Keep `npm run test:storybook` as the single command. The screenshots run
   inside it, so CI needs no new step and no new job.
5. Add `npm run test:visual:update`, which runs the same project with
   `--update`, for the approval path below.

The run cost is the capture time for the matrix on top of the current 25
seconds. Measure it against the CI budget during implementation, and split the
screenshots into their own job if the total passes the budget.

## Sketch: Baseline Review Workflow

1. A developer changes a component. CI fails the `storybook` step and names the
   stories whose pixels moved.
2. CI uploads the actual, expected, and diff images as a workflow artifact. The
   reviewer downloads one zip file.
3. If the change is wrong, the developer fixes the component.
4. If the change is intended, the developer starts the `workflow_dispatch` job
   `update-visual-baselines` against the PR branch. The job runs
   `npm run test:visual:update` in the same Ubuntu container as CI and pushes
   the new PNG files to the branch.
5. The reviewer reads the new PNG files in the GitHub "Files changed" view,
   which renders an image diff with a swipe control. The approval is the PR
   approval. No second tool.

Rule for the implementation ticket: a baseline generated on a developer machine
is never committed. Only the CI job writes baselines.

## Risks And Limits

- **Review noise.** 1000 snapshots on a shared component means 1000 red diffs
  for one intended change. Start with layout-bearing components and pages, and
  grow the set.
- **Repository size.** PNG baselines are binary. A redesign rewrites all of
  them, and Git keeps every version.
- **Platform drift.** The baseline name carries the browser and the platform,
  which prevents a silent mismatch. It does not prevent a developer from
  committing a macOS baseline that CI never reads. The CI-only update rule
  covers this.
- **Font loading.** A screenshot taken before a web font loads catches the
  fallback font, which is a real regression in one case and a flake in the
  other. The helper must wait for `document.fonts.ready` before it captures.
- **No vendor support.** A broken comparator is our problem. The counterweight
  is that `pixelmatch` is the same algorithm the open-source tools use.
